# CareerPilot

**Claude Code를 취준 전담 AI 컨설턴트로 만드는 템플릿.**
채용 전문가 페르소나 · 위키형 파일 메모리 · 멀티에이전트 워크플로우 — 실제 대기업 지원 캠페인 한 시즌을 이 구조로 운영하며 다듬었다.

## 왜 이게 필요한가

맨 Claude에게 자소서 첨삭을 시키면 **일반론**이 나온다. 근거 없는 칭찬, 어느 회사에나 통하는 조언, 세션이 끝나면 사라지는 맥락. 이 템플릿은 세 가지로 그걸 바꾼다:

> **도씨에(dossier)** — 한 주제(프로젝트·경력)의 검증된 사실만 모아 둔 근거 파일. 이 템플릿의 핵심 단위로, 첨삭·면접 답변의 모든 수치와 주장은 도씨에에 근거해야 한다.

| 상황 | 맨 Claude | 이 템플릿 |
|---|---|---|
| 자소서 첨삭을 시키면 | 누구에게나 통하는 일반론 | **검토관 시점** — 30초 안에 탈락 사유부터 짚는다 |
| 근거 없는 수치를 쓰면 | 그대로 통과 | `memory/` 도씨에와 대조해 **반려** |
| 내일 세션을 새로 열면 | 처음부터 다시 설명 | 회사별 상태·복기·교훈이 **git으로 이어진다 — 어느 PC에서든** |
| 기업 리서치를 시키면 | 검색 몇 번으로 요약 | **병렬 조사 + 적대적 재검증** — 공채 폐지·전형 개편까지 잡는다 |

실제 첨삭은 이런 문장으로 돌아온다:

> *"검토관은 30초 안에 이 문단에서 이탈합니다. 두 번째 문장의 수치가 도씨에에 없는데, 근거가 뭔가요?"*

## 5분 시작

```bash
# 1. Use this template 버튼으로 본인 소유 private 레포 생성  
#    ⚠️ 지원서·개인정보가 쌓이므로 반드시 private
# 2. 클론 후 CLAUDE.md 상단 빈칸(이름·github) 채우기
git clone https://github.com/<본인계정>/<본인레포>.git && cd <본인레포>
# 3. Claude Code 실행
claude
```

첫 세션에서 이렇게 요청하면 된다:

> "내 프로젝트 자료(README·발표자료·이력서 초안)를 줄게. ./memory/에 도씨에를 만들어줘."

이 도씨에가 이후 모든 첨삭·면접 답변의 **근거 원장**이 된다. 도씨에 없이 첨삭하면 일반론이 나온다 — 이게 이 템플릿의 제1원칙이다.

## 구성 요소

### 1) 채용 전문가 페르소나 — `CLAUDE.md`
"10년차 서류 검토관이 30초~3분 안에 무엇을 보고 통과/탈락을 가르는가" 관점. 듣기 좋은 말 대신 합격 확률을 바꾸는 지적만 하도록 행동 원칙 8개를 강제한다 — 기획은 실증 검증 후 착수, 제출물 문체는 사람냄새(수치 불가침), 디자인은 대상 기업 인접(모사 금지). 서브에이전트·워크플로우까지 같은 페르소나를 상속한다.

### 2) 위키형 파일 메모리 — `memory/`
```
memory/
├── companies/<회사>/status.md   # 회사별 "현재 상태" 페이지 — 상태 1줄 + [확정]/[예상]/[미확인] 일정 + 다음 액션
├── job-applications-<시즌>.md   # 캠페인 연대기 — append-only 히스토리 로그
├── projects/                    # 프로젝트 도씨에 — 자소서 수치·역할 주장의 근거 원장
└── rules/                       # 실수에서 얻은 교훈을 Why/How to apply로 박제
```
핵심은 **이원화**: "지금 어느 단계인가"(status)와 "무슨 일이 있었나"(연대기)를 분리해서, 세션이 바뀌어도 Claude가 1분 안에 상황을 복원한다. 상세 규칙은 [memory/README.md](memory/README.md).

### 3) 작업 산출물 + 로컬 코테 저지 — `산출물/`
```
산출물/
├── 지원서/<회사>/           # 회사별 — 제출물/(자소서·이력서) · 검증/(검수·팩트체크) · 자료/(설명회·커뮤니티)
├── 코테/
│   ├── 문제/<슬러그>/       # 문제.md · solution.py · testcases.json — 실전 문제 재구성
│   ├── 전략/ 복기/ 치트시트/ # 학습 자산 (전략 로드맵·복기 기록·템플릿)
│   └── judge.py             # 채점기 — 예제 실행 / --submit 전체 채점
└── 캠페인/                  # 시즌 로드맵·기업 캘린더 등 공통 전략
```
핵심은 **실전 재현**: 실전에서 만난 문제를 재구성해 프로그래머스처럼 제출·채점한다 — 케이스별 시간 제한(효율성 채점)·부분 점수까지 그대로, 채점 정답 데이터는 Claude가 브루트포스 대조로 생성한다. 상세 규칙은 [산출물/README.md](산출물/README.md).

### 4) 멀티에이전트 워크플로우 — `.claude/workflows/`
```
.claude/workflows/
├── company-research.js      # 공식 소스 / 응시 후기 / 정책 변화 스캔 3방향 병렬 → [확정]/[예상]/[미확인] 종합
├── essay-review.js          # 검토관 시뮬·사실/수치 검증·요건 대조·차별화 4렌즈 병렬 → 지적별 재검증
├── coding-test-debrief.js   # 코테 직후: 후기 수집 + 정답 구현·브루트포스 검증 + 이후 일정 확인
├── plan-verify.js           # 산출물 기획 검증: 합격 사례·업계 통념·기업 방향성 조사 → 스코프 판정 (만들기 전에)
└── openings-sweep.js        # 공채·수시 통합 스윕: 모든 감시 단위에 2축(회차 감시+수시 신입핏 스캔) 적용 → 변화 재검증
```
핵심은 **적대적 검증**: 병렬 조사·검토 결과를 그대로 믿지 않고 재검증 단계로 틀린 정보와 틀린 지적을 걸러낸다. "essay-review 워크플로우로 이 자소서 검토해줘"라고 말하면 실행된다.

## 실제 운영 기록

- **정책 변화 감지**: 캘린더 조사 중 한 대기업의 "작년 공채 실적"을 올해 일정으로 오인 → 재검증 워크플로우(6에이전트)가 **신입 채용이 채용 연계형으로 전환된 것**을 적발. 이후 "직전 회차 실적 ≠ 올해 정책" 규칙이 `rules/`에 박제되고 `company-research`에 내장됐다.
- **코테 복기**: 시험장에서 못 푼 그래프 문제를 응시자 기억만으로 재구성 → 정답 알고리즘을 구현하고 **브루트포스 1,500케이스 교차 검증** → 면접 코테 리뷰 카드로 전환.
- **제출 전 검증**: 자소서 최종본의 사실 주장 56개를 도씨에·커밋 로그와 전수 대조 — 오류 0건으로 제출.
- **감시 사각 적발 2건**: ①회사를 "공채 감시용/수시 스캔용"으로 나눠 운영하다, 정기 공채를 폐지하고 수시로만 신입을 뽑는 대기업 그룹들이 통째로 사각이 된 것을 적발 → 2축 매트릭스로 재설계(`openings-sweep`에 내장). ②감시용으로 확보한 채용 API가 실은 동명 기업의 다른 채용 채널 백엔드였음을 적대적 재검증이 적발 — "공고 전멸" 오신호를 걸러냈고, "감시 채널은 정본 백엔드인지 검증 후 신뢰" 규칙이 박제됐다.

같은 실수를 두 번 하지 않도록, 사고가 날 때마다 교훈이 `rules/`에 쌓이고 워크플로우 프롬프트에 반영된다. **시작은 템플릿이지만, 쓸수록 운영 체계가 된다.**

## 잘 쓰는 요령

- **사실 검증을 습관화** — "이 수치 근거 있어?"라고 물으면 페르소나가 검증 모드로 돈다. 후기·커뮤니티 정보는 작성 시점·회차 확인을 요구하라.
- **단계 연결** — 서류가 끝나면 코테 전략, 코테가 끝나면 면접 카드. "다음 단계 대비까지"를 요구하라.
- **복기 문화** — 코테·면접이 끝나면 결과와 막힌 지점을 던지고 복기를 요청하라. 기록이 쌓일수록 코칭이 정밀해진다.
- **세션 루틴** — 시작 `git pull`, 종료 커밋+`git push`. 한 번에 한 PC. (상세: [세팅_사용법.md](세팅_사용법.md))
- **만들기 전에 검증** — 포트폴리오·프로젝트 기획은 `plan-verify` 워크플로우로 합격 사례·업계 통념부터 확인하라. 스코프는 열정이 아니라 실증이 정한다.
- **원석 메모 문화** — 면접 답변·서사가 문득 떠오르면 다듬지 말고 그대로 던져라. 원문 보존 후 나중에 함께 다듬는 것이 워딩부터 만드는 것보다 낫다.
- **공채와 수시는 회사 구분이 아니라 질문 구분** — 회사를 "공채용/수시용"으로 나누면, 정기 공채를 폐지하고 수시로만 신입을 뽑는 그룹이 통째로 사각이 된다. 모든 감시 대상에 "회차가 떴나"(축①)와 "수시 보드에 신입 가능 포지션이 있나"(축②)를 함께 물어라. 그룹사는 통합 채용 보드 단위로 스캔하면 계열 수십 곳이 한 번에 커버된다 — `openings-sweep` 워크플로우가 이 구조를 강제한다.
